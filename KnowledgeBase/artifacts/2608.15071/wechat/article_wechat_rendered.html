一句话导读：论文提出"在线装备学习（online harness learning）"设定——冻结的 LLM agent 在顺序任务流上只靠持续更新一份外部技能清单来变强；Evo-Harness 把每次执行（通常只有一次机会）的嘈杂上下文编译成通用技能与主题技能两层装备，在 Claude Opus 4.6 上把 TerminalBench-2 成功率从 62.92 提升到 73.03，五个基准全部超过 No-Evolve 与 XSkill 等基线。

01论文速览
  • 研究问题：真实环境中的 agent 会连续遇到新任务，每次执行只给一次改进机会，产生的上下文噪声极大——有用的通用教训与任务专属细节纠缠在一起。已有经验学习方法多在离线轨迹池上挖规律，既少在复杂真实任务上严格验证，也没有拆解"到底是什么因素让 agent 变强"。
  • 核心方法：Evo-Harness 把 harness（一份外部结构化技能条目集合）当作学习介质，solver 参数全程冻结。执行失败后由 solver 反思产出候选记忆 ，再由 evolver 以 Add/Merge/Revise/Skip 四种编辑把候选记忆编译进 harness，形成跨任务通用模式（general）与任务类型流程（topic）两层。
  • 主要结果：以 Claude Opus 4.6 为 solver，五个基准成功率全部第一：CL-Bench 29.54→34.02、TerminalBench-2 62.92→73.03、SWE-bench Lite 63.67→67.00、τ-bench 72.73→76.97、WebArena-Infinity 72.50→76.25；最强基线 XSkill 相应为 31.44 / 66.29 / 64.67 / 73.94 / 73.75。
  • 一句话评价：这不是靠新训练目标取胜的工作，价值在于把"agent 在线自我改进"形式化成一个可控、可拆解、可解释的实验台，并用多组单变量诊断把"反馈从哪来、谁来做演化、技能能不能迁移"讲清楚了；代价是绝对增益不大、方差未报告，且高度依赖强 solver。
02研究背景与问题

LLM agent 已被用于 web 交互、软件工程、工具调用和长程推理等场景，这类任务要求 agent 会规划、会行动、会解读观测、会处理反馈并从错误中恢复。但论文指出的核心症结很简单：agent 在一次任务上失败后，这次失败往往只是一个孤立事件，而不是未来改进的来源。不把失败执行转换成可复用的教训，agent 会在后续任务里继续犯同类错误。这一"经验不沉淀"的问题，正是自演化 agent 研究的出发点。

现有做法大致分四类：反思（reflection，如 Reflexion）、记忆（memory，如 MemoryBank、Mem0）、规则（rules，如 AutoManual）与技能（skills，如 XSkill、SkillRL、AutoSkill）。它们大多在积累下来的轨迹池上离线挖掘规律，把产物当作被动仓库供自由检索。论文认为这与真实设定错位：真实环境中任务是顺序到来的新任务，每次完整执行通常只提供一次机会去影响未来行为；而真实执行产出的上下文又极其嘈杂，把有用教训与任务专属细节、部分失败、偶然的工具调用轨迹混在一起。如图 2 所示，左侧"检索过去案例"与右侧"把经验编译成可复用指导"是两种不同的信息流向。

— 图 2：经验复用的两种范式对比——左侧是检索过去案例，右侧是把经验编译成可复用的技能指导

更关键的是，论文给出了一条诊断性证据：外部经验复用并不自动有益。在主实验里，AWM 在 CL-Bench（28.91）、SWE-bench Lite（62.67）、τ-bench（70.91）、WebArena-Infinity（70.00）四个基准上都低于完全不做演化的 No-Evolve（29.54 / 63.67 / 72.73 / 72.50）；Dynamic Cheatsheet 的两个变体 DC-Cu、DC-RS 也普遍偏低。这说明检索或演化出来的指导可能是噪声、可能过度贴合某个具体任务，也可能与 solver 的能力不匹配——"加了记忆反而更差"。

由此论文提出两个空白：一是缺乏在真实在线约束下对经验学习方法的严格验证，二是缺乏对"改进由什么驱动"的系统性隔离。作者的主张是：在一-shot、高噪声的学习环境里，简单检索历史经验不够用，agent 需要主动把原始执行上下文编译成面向新任务的技能指导，并且这个编译过程本身要成为可被实验解剖的对象。

03核心思路

论文的关键观察是：一次执行的价值不在于"这次具体做了什么"，而在于"下次遇到同类情形应该怎么做"。轨迹是案例，案例检索只能告诉 agent"以前有人这么干过"；而技能是操作知识，它规定 agent 应当如何规划、如何验证、如何从失败恢复。因此学习介质应该从"记忆库"换成"harness"——一个外部的、结构化的、被主动编辑而非被动追加的条目集合。这一转变带来的直接好处是：harness 天然带注入预算，条目必须精炼才有机会被选中，噪声无法靠"越存越多"来稀释。

由此推出整体设计：solver 冻结，只有 harness 变。这既贴近很多 agent 只能调 prompt、不能改权重的工程现实，也把学习过程变成了一个干净的单变量实验：既然模型参数不动，性能变化就只能归因于 harness 的内容与更新方式。图 3 对比了三种设定：以往方法离线收集执行、事后挖规律；真实在线流中任务顺序到来、经验一次即弃；本文把在线经验编译成持续演化的技能装备。

— 图 3：问题设定对比——(a) 离线挖掘；(b) 真实在线流中一次性的执行经验；(c) 本文把在线经验编译成持续演化的技能装备

双层结构（general / topic）则是对噪声的直接回应。跨任务比较能过滤掉只在单个任务成立的细节，留下共享的操作结构；任务类型流程则保留局部化的界面、接口、领域知识。论文特别强调，这两层不是给执行预先打的标签，而是 evolver 在过滤、比较、整合候选记忆的过程中自然涌现出来的分类。相应地，更新以批（batch）为单位进行：只有同一批里有多个任务，evolver 才有机会横向比较、提炼跨任务模式；当批大小为 1 时，该形式化退化为纯粹的任务类型更新。

04方法详解

整体框架

输入是一条任务批流 {B1,…,BK}、一个冻结的 solver 𝒜 和初始 harness ℋ1；输出是演化后的 harness ℋK+1 与各任务执行结果。在第 i 批开始前，harness 是一组结构化条目 ℋi={hi1,…,hini}。对批内每个任务 xi,j，系统先按注入预算 b 选出至多 b 条相关条目，注入任务描述后交给 solver 执行；执行产出的轨迹 τ、结果 y、反馈 f 与原任务一起构成执行上下文。批内任务全部跑完后，反思模块把每个上下文转成候选记忆，evolver 再把这些候选记忆与当前 harness 对照，编译出一组编辑并应用，得到 ℋi+1。

用公式表示，注入与执行是：

\mathcal{S}_{i,j}=\mathrm{Select}(x_{i,j},\mathcal{H}_i;b),\quad (\tau_{i,j},y_{i,j},f_{i,j})=\mathcal{A}\big(\mathrm{Inject}(x_{i,j},\mathcal{S}_{i,j})\big)

其中 𝒮i,j 是选中的条目集合（大小不超过预算 b），Inject 把选中的指导拼进任务上下文，τ 是动作轨迹、y 是任务结果、f 是可获得的反馈（验证器结果、单元测试输出、工具诊断、judge 反馈等）；四元组 ci,j=(xi,j,τi,j,yi,j,fi,j) 就是后续反思的输入。

值得注意的是这个框架里没有任何训练目标或梯度更新。全部"学习"发生在推理期，通过两次额外的 LLM 调用完成：每个任务后一次反思，每一批结束后一次演化。模块划分被刻意解耦为 solver、evolver、反馈源、初始 harness 四个可独立替换的部分——这正是后面 RQ3、RQ4 能做单变量对照的前提。

只从失败中提取候选记忆（execution reflection）

这一步要解决的是噪声问题。真实执行的上下文里混着成功路径上的偶然细节，若不加筛选地总结，harness 会被"这次用了某个特定命令"这类无关信息污染。论文的做法是：只有当执行失败或收到负面反馈时，才对该上下文做反思，

即每条候选记忆由四部分组成：可复用的做法（lesson）、触发条件（trigger）、本次失败的证据（evidence）、适用范围提示（scope_hint）。反思使用执行后立即可得的完整任务侧上下文，包括指令、轨迹、观测、工具输出、结果与反馈。

为什么只反思失败？论文的解释是失败暴露了 solver 当前的能力边界：错误的假设、被忽略的约束、无效的工具使用、薄弱的验证、失败的恢复。这些比成功执行更能指出"下一次该怎么改"，同时避免了成功路径中任务专属细节带来的无谓更新。

另一个容易被忽略的设计是：反思阶段不与当前 harness 比较，因此它的输出不是最终更新，而只是一个"以失败为锚"的候选信号。把"提取"与"合并"彻底分开，使得后面 evolver 可以在看到整批候选记忆的前提下统一决策，而不是逐条即时写入。

用 evolver 做编辑而不是追加（harness evolution）

第二步要解决的是冗余与冲突。一批任务可能产出十几条候选记忆，彼此重叠甚至矛盾；如果直接 append，harness 会长得很快，而每次注入只有 b 条预算，条目越多、每条被选中的概率越低，等于自我稀释。论文让 evolver 同时读取候选记忆集合 ℛi 与当前 harness ℋi，输出一组编辑：

o=\pi_{\mathrm{evolve}}(r,\mathcal{H}_i,\mathcal{R}_i),\quad o\in\{\textsc{Add},\textsc{Merge},\textsc{Revise},\textsc{Skip}\},\quad \mathcal{H}_{i+1}=\mathrm{ApplyEdits}(\mathcal{H}_i,\mathcal{O}_i)

也就是说，每条候选记忆可以被新增为条目、与已有条目合并、用来修订已有条目的表述，或者被直接丢弃。四种动作里 Skip 是最关键的：它让 harness 具备"拒绝学习"的能力，从而把一次性执行里的偶然噪声挡在门外；Merge 与 Revise 则保证 harness 保持紧凑，不会随任务流线性膨胀。

批级更新是这套设计的必要条件。只有看到同一批内多个任务的候选记忆，evolver 才能判断哪些教训是重复出现的（值得 Add）、哪些只是同一模式的变体（应当 Merge）、哪些相互冲突需要改写（Revise）。这一步也是"编译"与"存储"的分水岭：候选记忆不会被原样写入，只有被判定为可复用的部分才会进入 harness 并影响未来行为。

两层 harness：跨任务通用模式与任务类型流程

演化出的 harness 包含两个层次的指导。跨任务通用模式由跨任务比较候选记忆、识别共享操作结构得到，回答"这类问题普遍该怎么处理"；任务类型流程保留更局部化的知识，针对反复出现的任务格式、界面或领域，回答"在这个接口/这套工具下具体怎么操作"。对应到算法里就是两个编译算子：CompileTaskType 保留局部流程，CompileCrossTask 抽取跨执行共享模式，二者并集后统一应用。

这一分层对应噪声过滤的两个方向：向上一层靠"多任务共现"筛掉偶然细节，向下一层靠"同类型复用"保留具体可执行的操作步骤。论文强调这两层不是对单次执行的预定义分类，而是 evolver 过滤与整合的副产物，因此它们的边界会随任务流自行漂移。这个设计是否真的必要，由后面的组件消融来回答。

05实验结果

实验设置

评测覆盖五个真实 agent 基准，分别考察不同能力：WebArena-Infinity 考察 web 导航，TerminalBench2 考察命令行任务，SWE-bench Lite 考察软件工程，CL-Bench 考察自适应推理，τ-bench 考察工具使用。默认 solver 与 evolver 均为 Claude Opus 4.6；研究模型泛化时替换为 Claude Opus 4.7、Opus 4.5、Kimi-K2.5 与 GPT-OSS。指标为成功率（%），越高越好。

对比基线覆盖经验、记忆、技能三条路线：AWM 复用 agent 工作记忆，Dynamic Cheatsheet 维护自适应外部速查表（DC-Cu 与 DC-RS 是两个变体），Evo-Memory 从执行中演化可复用记忆，ACE 优化 agent 上下文，XSkill 把经验与技能分离以便持续复用；No-Evolve（不做任何 harness 更新）作为下界。所有方法在相同任务划分与评测协议下比较。

主要结果

表 1 给出 Opus 4.6 作为 solver 时的主结果。本文方法在五个基准上全部取得最好成绩，且是唯一同时超过 No-Evolve 与全部基线的方法。增益最大的是 TerminalBench-2：从 62.92 提升到 73.03，绝对提升 10.11 个点。论文对这一点的解释是，命令行任务需要检查文件、执行命令、解读错误、从失败操作中恢复，天然暴露大量可复用的程序性结构，正好落在 harness 擅长编码的内容上。

在模型泛化上，CL-Bench 的五模型结果显示本文方法对每个模型都有提升，但幅度与模型能力相关：Opus 4.7、Opus 4.6、Opus 4.5 分别提升 3.7、4.5、3.8 点，而 Kimi-K2.5 与 GPT-OSS 只提升 1.1 与 0.8 点。分类别看，程序性任务执行（PTE）最稳定，五个模型全部提升，Opus 4.6 与 Opus 4.5 各提升 9.8 点；而经验发现与仿真（EDS）最不稳定，Opus 4.6 下降 2.5 点、GPT-OSS 下降 1.0 点，作者认为探索性任务对过于具体的指导更敏感。

反馈来源（表 3）是全文最有实践价值的一组：让 LLM 自己判断成败（Self-Generated）在两个基准上都低于 No-Evolve（CL-Bench 29.54→27.96，SWE-bench Lite 63.67→61.67），说明缺乏外部证据锚定的自评会引入误导性更新。只用环境给出的成败信号（Minimal）恢复并超过基线（29.86 / 67.33），而带诊断信息的 Standard 反馈在 CL-Bench 上最好（34.02），在 SWE-bench Lite 上反而略低于 Minimal（67.00 对 67.33）。作者的解释是，详细报错有时会让 harness 过度绑定到具体失败案例，稀疏的 pass/fail 反而鼓励更通用的指导。

06局限与思考

这篇论文真正的新意不在"从经验中学习"这个概念本身，而在于两点方法论上的选择：其一，把在线顺序学习形式化为"冻结 solver + 只更新外部 harness"，从而把变量集中到一个可读的文本对象上；其二，把 harness 当作可解释的分析对象而不是单纯的性能补丁，用它来隔离反馈来源、evolver 配对、迁移方式这些驱动因素。同类工作大多只报聚合成功率，这篇给出了"加记忆为什么会变差"的具体证据。

就证据强度而言，主结果比较扎实：五个形态差异很大的基准方向一致，且基线在相同任务划分与协议下重跑，TerminalBench-2 上 +10.11 的幅度不太可能是偶然。组件消融与反馈消融的方向也彼此印证（有外部锚定的反馈优于自评，通用与局部两层各有其适用面）。但有一个明显缺口：论文未报告任何方差、置信区间或多种子结果。像 SWE-bench Lite 上 Minimal 的 67.33 对 Standard 的 67.00、Cross 的 76.0 对 Same 的 75.3，这类 0.3~0.7 点的差异很可能落在单次运行的噪声范围内，作者却给了较强的定性解读。这是我认为读者应当保留意见的地方。

几个隐含假设也值得点出。第一，方法隐含假定任务流中存在可被利用的重复结构——general 与 topic 两层都建立在"同类任务会再次出现"之上；EDS 类探索任务上 Opus 4.6 掉 2.5 点，正是这一假设失效时的表现。第二，方法隐含假定 solver 足够强：Sonnet solver 下无论同模型还是跨模型演化都低于 No-Evolve，意味着这套流程在弱模型上可能是负收益，而论文的默认 solver 是 Claude Opus 级别。第三，反思与演化都由 LLM 完成，每个任务一次反思、每批一次演化，且 harness 增长后选择阶段的上下文成本上升，但论文未报告任何 token 或时间开销。

最后是论文自己承认、也容易补的局限：只覆盖单 agent、纯文本的工具/命令行/web/软件工程环境，未涉及具身或多 agent 场景（后者中 harness 还要处理协调与环境反馈）；harness 只用自然语言指导实例化，可执行代码技能或结构化程序等形态未探索。此外还有一些未披露的关键量：注入预算 b、harness 的条目规模、批大小的取值，都没有在正文给出，这会影响复现。对工程实践而言，可借鉴的模式是清晰的：经验条目要带触发条件与证据、更新要走显式的新增/合并/修订/丢弃、注入要有预算上限——这比无脑往记忆库里 append 要可控得多。

07总结

论文要解决的问题是：真实环境中的 agent 每次执行只有一次改进机会，产生的上下文既嘈杂又难以沉淀，而现有经验复用方法在真实任务上未必有效。它的解法是把学习介质从"记忆库"换成"外部技能装备"：solver 冻结，执行失败后反思出带触发条件与证据的候选记忆，再由 evolver 以新增/合并/修订/丢弃四种编辑编译成通用与主题两层 harness。在五个真实基准、Claude Opus 4.6 solver 下，该方法全部取得最佳成功率（TerminalBench-2 从 62.92 到 73.03，SWE-bench Lite 从 63.67 到 67.00），并通过反馈来源、evolver 配对与迁移三组诊断说明"有外部锚定的反馈"和"能读懂指导的 solver"是自我改进成立的两个前提。最值得记住的一点是：经验的价值不在于被存下来，而在于被编译成下一次可以直接执行的操作知识。

08科学发现范式
  • 主要范式：P01 Gap-Driven Reframing
  • 次要范式：P04 Modular Pipeline Composition, P03 Representation Shift & Primitive Recasting, P09 Inference-Time Control & Guided Sampling
  • 分类理由：该论文从离线经验挖掘在真实在线流中仅有一次性机会、上下文噪声大的局限出发，将问题重构为在线 harness 学习，使冻结 agent 通过更新外部 harness 持续改进，故主模式为 P01。方法上将求解器反思与演化器更新组织为可复用技能编译流水线，并把经验载体从被动检索转为 general/topic 结构化技能表示，同时属于不改模型参数的推理时外部自适应，故次模式为 P04、P03、P09。
09先前工作分析

"Reflexion" 把失败轨迹转成语言化反思并回灌到后续尝试，"ExpeL" 则从大量累积轨迹中离线抽取自然语言 insight 与规则，二者共同确立了“经验可转化为指导”的范式，但都依赖单任务迭代或多轨迹池。"AutoManual" 进一步让 agent 在交互中自动构建 instruction manual，把环境经验固化为可执行规则；"Voyager" 用可执行代码技能库支撑终身学习，证明外部技能组件能被复用并迁移。"ReasoningBank" 将推理策略沉淀为可检索的经验库，"MemoryBank" 维护长期记忆并按需检索历史，它们展示了结构化外部存储的价值，却仍把经验当作被动仓库。"GEPA" 用自然语言反思驱动 prompt 演化，说明不更新参数也能通过 reflective evolution 改进 agent，这为 harness 的 evolver 提供了直接启发。这些工作合起来留下一个明显缺口：经验提取要么离线、要么单任务、要么停留在被动检索，缺少在真实任务流中把一次执行在线编译为主动结构化指导的机制。Evo-Harness 因而将反思、规则、技能库与演化式更新综合为 context-to-harness skill compilation，用 solver 提议候选技能、evolver 维护 general/topic skill harness，从而在 one-shot 在线场景中把噪声执行上下文转化为可复用、可解释的外部学习支架。
